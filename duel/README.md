# phira-duel —— Phira 双人对战（自研协议 + 服务端）

双人对战模式的服务端与协议。**和标准联机（phira-mp）是并列的两条路**：
标准联机继续走 phira-mp，这里只负责新玩法。

## 为什么自研

| phira-mp 里有但这里不需要 | 原因 |
|---|---|
| 谱面信息从官方 API 拉、谱面要传 | 两个玩家**本地都有谱面**，服务端只交换谱面 ID |
| 玩家 token 去官方 API 鉴权 | 朋友之间玩，v1 不做鉴权（要加也是可选） |
| 聊天 / 锁房 / 房主轮换 / 房间列表 | 对战模式用不上 |

抛开这些之后，服务端**不碰谱面和音频**，只转发事件，于是协议很小、跑起来很轻。

**代价（认下来的）**：这套协议只有本修改版的 App 能用，官方服务器和其它客户端永远用不了。

## 玩法规则（v1）

**赛制**：BO3，两胜结束。

**BP 选曲**（曲池 = 双方本地曲库的交集，服务端求交集后下发）：

```
A ban 1 张 → B ban 1 张 → A pick 1 张（第 1 局）→ B pick 1 张（第 2 局）
若 1:1 → 由「上一局的败者」从剩下的池子里 pick 1 张打决胜局
```

胜负：分数高者胜；同分比准度；都一样算平局（不加胜场）。

**能量与干扰**：

- 能量由客户端按自己的判定上报（Perfect / Good 攒，上限 100）；服务端上限钳制。
- 开局后 **10 秒内禁止投干扰**（`cast_lock_ms`）。
- 每种干扰**独立冷却 8 秒**（`cooldown_ms`）。
- 投出的干扰**只发给对手**，对手界面要明确提示"谁对你用了什么"。
- 能量不够 / 冷却中 / 开局锁定 → 服务端返回 `CastDenied` 并说明原因。

| 干扰 | 效果 | 消耗 | 时长 |
|---|---|---|---|
| 迷雾 `Fog` | 判定线附近叠一层雾，挡视线 | 30 | 2.5s |
| 抖线 `Shake` | 判定线渲染时叠加晃动 | 35 | 2.5s |
| 噪点 `Noise` | 屏幕叠一层噪点条纹 | 25 | 2.0s |
| 压暗 `Dim` | 整体压暗 | 40 | 2.5s |

> v1 **只做纯视觉干扰**。「变速」「左右反转」这类会动到判定/时间轴的干扰先不做——
> 它们要改 `TimeManager` / 判定坐标，出错就是整局判定错乱，风险远大于收益。

**掉线**：对局中途掉线直接判另一方获胜，不让剩下的人干等。
**房间**：v1 一台服务器同时只有一个房间；房间码由第一个进房的人设定，第二个必须一致。
两个人都走光后房间自动重置（房间码、曲池、比分全清），下一组人可以用新房间码开新局。

## 协议

帧格式：`[u32 小端长度][JSON]`，单帧上限 1 MiB。
用 JSON 而不是二进制：每局只有几十~几百条消息（触摸不上传、谱面不上传），
省字节没意义，**排错时能直接看懂抓包**才有意义。

### 客户端 → 服务端

| 消息 | 说明 |
|---|---|
| `Hello { room, name, charts }` | 进房；`charts` 是本地谱面 ID 列表，用来求曲池交集 |
| `Ban { chart }` / `Pick { chart }` | BP 操作（服务端校验轮次与可选范围） |
| `Progress { score, accuracy, combo, energy }` | 打歌中上报，用于显示分差和能量 |
| `Cast { kind }` | 投干扰 |
| `Finish { score, accuracy, max_combo, counts }` | 交卷 |
| `Ping { at }` / `Leave` | 保活 / 主动离开 |

### 服务端 → 客户端

| 消息 | 说明 |
|---|---|
| `Welcome { you, room, players }` | 进房成功，`you` 是 0/1 号位 |
| `PeerJoined` / `PeerLeft` | 对手进出 |
| `Pool { charts }` | 双方曲池交集 |
| `BpTurn { actor, action, pool, decider }` | 轮到谁 ban/pick；`decider` 表示这是决胜局选曲 |
| `BpDone { chart_a, chart_b }` | 第 1、2 局的谱面 |
| `RoundStart { index, chart, starts_in_ms }` | 开局；**相对时间**，各端用自己的时钟算，不需要对表 |
| `PeerProgress { ... }` | 对手进度 |
| `CastOk { kind, energy }` / `CastDenied { kind, reason }` | 投递结果 |
| `Attacked { kind, from, duration_ms }` | 你被干扰了（只发给被打的一方） |
| `RoundEnd { index, winner, scores, next }` | 本局结算 + 下一步（下一局 / 回 BP / 结束） |
| `MatchEnd { winner, scores, reason }` | 比赛结束（`reason` 含比分或掉线说明） |
| `Notice { message }` | 提示（谁 ban 了哪张） |
| `Error { message }` / `Pong { at }` | 错误 / 心跳回复 |

## 自测（不需要两台设备）

```bash
cd duel
cargo test
```

`tests/match.rs` 在进程里起服务端、塞两个客户端，把一整场走完：
进房 → 曲池交集 → BP 四步 → 第 1 局 → 投干扰（成功 + 能量不足被拒 + 冷却被拒）
→ 交卷结算 → 第 2 局 → 1:1 → 败者选决胜曲 → 第 3 局 → `MatchEnd`。
另外两个测试覆盖房间码校验和中途掉线结算。

这套测试已经抓出两个真问题（写在这里免得以后重犯）：

1. **客户端异常断开（RST）时 `on_disconnect` 没执行** —— 循环里直接 `?` 会在出错时
   提前 return，玩家永远留在房间里，房间不复位、后来的人用新房间码进不来。
   现在循环包在 async 块里，无论怎么退出都会执行清理。
2. **房间码锁死** —— 打完一局人都走光后房间不重置，下一组人没法开新局。
